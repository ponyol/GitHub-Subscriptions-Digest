Устранены критические проблемы безопасности (например, при распаковке tar-архивов) и исправлены ошибки, связанные с согласованностью каталога.

CockroachDB is stricter than PostgreSQL about SQL type coercion: aggregate and extraction functions return different numeric types, and some operators require their operands to share a type. Several query translations were updated to add explicit casts so that results come back with the expected types and queries no longer fail or return incorrect values on CockroachDB. These changes are transparent on PostgreSQL. In the course of this work we also found and fixed a latent bug in the microsecond extraction logic that produced incorrect results on PostgreSQL as well, and added a regression test that exercises sub-second values. Tests covering features that are not yet supported on CockroachDB are skipped when running against that backend. Finally, a dependency constraint was adjusted so that the environment builds on linux/aarch64. Same check that already exists in `begin_xact()` - Make validation stronger by taking into account `lock_mutable_tree` - On the happy path, this check should add no new I/O - fix(share): pass filter='data' to tarfile.extractall on table restore (#1378) Closes #1376 (per @aaron-siegel's request). ## Change One-line addition of the `filter='data'` keyword to the `tarfile.extractall()` call on `TableRestorer.restore()`: ```diff with tarfile.open(bundle_path, 'r:bz2') as tf: - tf.extractall(path=self.tmp_dir) + tf.extractall(path=self.tmp_dir, filter='data') ``` ## Why `tarfile.extractall()` without an explicit filter is the [CVE-2007-4559](https://cve.mitre.org/cgi-bin/cvename.cgi?name=CVE-2007-4559) class — a malicious tar entry with `..` path components or a symlink pointing outside the destination is extracted as-is. Because `TableRestorer.restore()` is the entry point for unpacking a bundle authored elsewhere (the whole `pixeltable/share/` subsystem exists to let users move tables between each other), this is on a code path that handles externally-sourced input by design. The `'data'` filter ([PEP 706](https://peps.python.org/pep-0706/)) rejects absolute paths, `..` traversal, special files (device nodes, FIFOs), and unsafe symlinks/hardlinks. It's the safer default Python recommends for any extraction from an external source and is scheduled to become the default in Python 3.14. ## Compatibility The `filter=` keyword was backported to all currently-supported Python versions (3.7–3.11) per PEP 706, so this works on every Python in pixeltable's `>=3.10` support range without raising a `TypeError`. ## Scope This PR intentionally addresses only the tarfile finding from #1376 — the SQL `text(f"...")` items in `pixeltable/catalog/*` and the workflow `${{ ... }}` shell-interpolation are best-practice items that don't have an exploitability shape today, and I'd file them as separate issues/PRs if useful rather than bundling them here. Co-authored-by: sergey-mkhitaryan <mkhitaryan.sergey@gmail.com> - remove autouse from fault_injection fixture (#1382) - Fix Catalog lock ordering (#1399) Fix the order in which Catalog acquires table locks: * writes before reads * whole tvps before individual tables Writes-before-reads is by convention, right now Catalog does not depend on it for correctness. But it's crucial to cache/lock the table paths before individual tables in order to guarantee the ancestor-first ordering of locking. Without this fix, the following scenario is possible: 1. There exist a base table, a mid_view on it, and a leaf_view on mid_view. Thread 0 has all 3 cached. 2. Thread 0 starts to validate its cache for a read in the following order: leaf_view individually, then base table's whole path (base table, mid_view, leaf_view) 3. Thread 1 drops leaf_view concurrently 4. When Thread 0 reaches mid_view in its validation loop, it notices that mid_view's view_sn changed, and reloads mid_view. mid_view no longer lists leaf_view in its mutable_views. 5. Thread 0 skips leaf_view validation the second time since it was validated first. 6. Thread 0's Catalog is in an inconsistent state: both leaf_view and mid_view are validated, yet mid_view does not list leaf_view as its mutable view. This scenario is very hard to deterministically reproduce and validate in a test without messing too much with Pixeltable internals, so not including a test. - Skip HF-dependent notebooks and unit tests in pull requests (#1398) Github secrets are not available in pr checks, and HuggingFace downloads consistently fail due to rate limiting without a token. Merge queue, on the other hand, runs in the context of the main repo, which means HF token is available, and we can expect much higher limits. This pr disables HF-dependent notebooks and tests in pull requests (i.e. when a commit is pushed), but leaves them enabled in merge queue tests. Those tests are now called "expensive", and what used to be "expensive" is now "very expensive". This terminology mirrors the existing tests terminology and its behavior.
