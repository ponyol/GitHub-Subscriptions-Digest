Суммаризация (на русском)

Это обновление устраняет критическое состояние гонки в методе `v3.close()` API Stagehand, которое ранее приводило к бесконечным зависаниям во время параллельных выполнений оценки, особенно в средах с высокой задержкой. Проблема возникала из-за закрытия веб-сокета CDP раньше, чем приходил HTTP-ответ клиента API, что приводило к неразрешенным промисам и непринятым вызовам CDP в процессе выполнения. Решение обеспечивает надежное завершение `close()` путем обработки уже закрытых веб-сокетов, отклонения всех ожидающих CDP-запросов при завершении работы сокета и предотвращения повторного входа в путь завершения работы.

the HTTP round-trip of `apiClient.end()` (client → API → client), and - the CDP websocket close event arriving from the browser race sequence: 1. `v3.close()` awaits `apiClient.end()` (HTTP request/response) 2. the API requests release immediately, and the browser closes the CDP websocket 3. the websocket `"close"` event can reach the client before the HTTP response returns 4. only after the HTTP response returns do we call `ctx.close()` → `CdpConnection.close()` if the close event wins the race and fires before step (4), then `CdpConnection.close()` attaches its one-shot `"close"` listener too late (the event already happened), so the promise never resolves. far regions make this more likely because the HTTP RTT is longer, increasing the window where the close event can beat the response. two additional issues were found in the same shutdown path: - inflight CDP calls are never rejected when the websocket closes unexpectedly. pending `send()` promises hang forever alongside `close()`, which compounds the original hang - the `_onCdpClosed` transport handler was still registered when `apiClient.end()` was called. the server-side websocket close would fire `_onCdpClosed` -> `_immediateShutdown()` -> `close({ force: true })`, re-entering the close path while the original `close()` was still in progress this bug only reproduced reliably with regions that are far away from the client machine because: - `apiClient.end()` awaits a full request/response to the hosted API; higher client-region latency makes that await longer - during that longer window, the server-side websocket close can arrive and be processed before `CdpConnection.close()` is called -
