- gptel: Separate query/response buffers more explicitly Fix edge cases arising from the ability to separate the query buffer from the response destination when using gptel-send. Clarifying gptel's model for separating the query source and response destination addresses most of them automatically. Conceptually: The query buffer is the one in which the request originates. It determines the gptel configuration to use. For example, the value of `gptel-tools' in this buffer is used, and tools run in this buffer. The response destination determines where and how response is inserted, the tool call confirmation UI is placed, and so on. This separation is enforced by setting gptel-request's :position argument to a marker in the destination buffer and using this buffer in the default insertion callback(s). This means that there is little reason to explicitly set gptel-request's :buffer argument any more. Needless to say, all of this applies only to gptel-send, since these distinctions are imposed on the gptel-request callback. * gptel-transient.el (gptel--suffix-send): Don't set :buffer when calling gptel-request, and make the :position argument a marker in the destination when it is a buffer. * gptel.el (gptel--handle-pre-insert): Check if the response buffer is read-only, not the query buffer. (gptel--display-tool-calls): Set up the tool call confirmation UI in the response buffer, not the query buffer. Add comments and improve documentation. - gptel-request: Improve gptel-backend-header arity warning * gptel-request.el (gptel--maybe-funcall): Improve the warning displayed when a gptel-backend-header/gptel-backend-url function accepts no arguments. Per recent changes they are now called with the request INFO plist. - gptel: Set use-context and use-tools in default preset * gptel.el (gptel--known-presets): Also set `gptel-use-context' and `gptel-use-tools' to their default values in the gptel-default preset. Note that we set both `gptel-context' and `gptel-tools' to nil here, but we still want context and tool use to be enabled since this is gptel's default behavior. - gptel: Add gptel-default preset to reset configuration * gptel.el (gptel--known-presets): Include a pre-defined preset named gptel-default. This preset "resets" most gptel settings to the default values that gptel ships with. This means no system prompt or tools, no additional context sources, no request temperature, max token limits and more. It does not change the active gptel-model or gptel-backend. This has at least two uses: 1. By applying the preset interactively, you can use it to quickly reset most of gptel's configuration back to the default (excepting the model and backend, which are nil by default). 2. When using `gptel-request' for scripting purposes, you can fully isolate the call from the effects of gptel's environment with (gptel-with-preset 'gptel-backend (gptel-request prompt ...)) Presets can also inherit from gptel-default to build a bespoke gptel configuration. Further rationale for this feature is explored in #1365. * NEWS (New features and UI changes): Mention gptel-default and the rationale for it. - gptel-request: Add -N flag to Curl invocation on all platforms * gptel-request.el (gptel-curl--common-args): The -N flag (no-buffering) was previously added for macOS in 4747ffa251af84dbb6fe181f5d2b484ec2e442a7, but 85126d398c800dfed80a91aac990a5dc0d15f9a6 caused a regression on Linux as well. Add it to the Curl invocation on all platforms. This is a tentative change, to be reverted if there are issues. - gptel-anthropic: Fix Claude Sonnet 4.6's context window * gptel-anthropic.el (gptel--anthropic-models): Fix context window size for claude-sonnet-4-6. - gptel-anthropic: Add support for Claude Opus 4.7 * gptel-anthropic.el (gptel--anthropic-models): Add support for Claude Opus 4.7. * NEWS (New models and backends): Mention addition. - gptel-gh: Add GitHub Copilot support for claude-opus-4.7 * gptel-gh.el (gptel--gh-models): GitHub Copilot now offers claude-opus-4.7. Add it with the same capabilities/properties as claude-opus-4.6. * NEWS (New models and backends): Mention change. - gptel: Fix gptel--preset-syms dropping parent-contributed symbols * gptel.el (gptel--preset-syms): The expression (nconc syms ...) in the :parents handler doesn't update syms when it's nil, so symbols contributed by parent presets are silently lost. This causes gptel-with-preset to not save/restore variables set by parent presets - they leak into the surrounding scope after the macro exits. Fix by wrapping in setq so the accumulator is always updated. Also simplify by `nconc'ing all parent symbols in one shot using `mapcan', rather than multiple `nconc' calls in a `map' call. - gptel-openai-extras: Add usage tracking for Perplexity * gptel-openai-extras.el (gptel--parse-response): Reuse OpenAI's non-streaming response parser in the Perplexity backend so that token tracking (and any future features) are automatically inherited. - gptel: Ensure newline after response when confirming tools * gptel.el (gptel--accept-tool-calls): Continuing the newline fix in 85895f2, fix the case of missing newlines between response text and tool result blocks when the tool call has been explicitly approved using gptel's tool confirmation overlay. This is an order-of-operations bug: - The tool confirmation overlay inserts tool call text into the buffer, including a trailing newline. - After confirming the tool call(s), `gptel--display-tool-results' runs before the confirmation overlay(s) are cleared. - It sees this trailing newline at the response tracking marker and assumes that no separator between the response text and tool result block is needed. - The tool result insertion happens, then the confirmation overlay is cleared, deleting the preview text and removing the separator newline in the process. Fix by reversing the order of operations: when accepting tool calls, first remove the overlays, then call the tools and insert results. What `gptel--display-tool-results' sees is now the state of the buffer that will persist, including any present/absent trailing newlines at the tracking marker.
