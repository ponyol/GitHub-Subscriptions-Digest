The issue stems from warp divergence during the execution of the UTCHMMA instruction. ## Root Cause Analysis Core dump extraction from the crashed MAX serve worker identified the exception as a Warp Illegal Instruction Parameter occurring at the UTCHMMA instruction in sm100_mha_depth256. In build_mma (which constructs the inline PTX for the MMA), lane 0 was the elected lane (@P0) and was responsible for setting UR13 via @P0 R2UR.BROADCAST UR13,R3. However, warp divergence split the execution: Wave front A (lane 0) correctly executed the broadcast, sets UR13, and executed UTCHMMA Wave front B (lanes 1-31) misses the update to UR13 and executes UTCHMMA with a bad operand If wave front B sets mbar after wave front A sets c_tmem, wave front B ends up using a corrupted/uninitialized UR13 address, crashing the kernel when it launches UTCHMMA. ## Solution This is resolved by modifying build_mma to hint to ptxas that the operand stored in UR13 is uniform across all lanes. By broadcasting c_tmem as the input to the inline assembly, ptxas emits an unguarded R2UR instruction, allowing every wave front to correctly execute the move. This also addresses the warp divergence causing UTCHMMA to be issued multiple times per warp. ```diff inlined_assembly[mma_string, NoneType, constraints="r,r,r,r,r,r,r,r"]( - c_tmem, 0, idesc, c_scale, b.lo, b.hi, elect, a + broadcast(c_tmem), 0, idesc, c_scale, b.lo, b.hi, elect, a ) ``` ## Why this approach? Two solutions were evaluated: this uniform broadcast hint (Solution 1) and electing a single lane to execute the entire MMA block like CUTLASS does (Solution 2). Solution 1 was selected because: SASS Quality: Avoids injecting new BSYNC.RECONVERGENT instructions, which build_mma was originally designed to avoid.
