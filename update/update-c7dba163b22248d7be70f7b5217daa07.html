Суммаризация (на русском)

This release delivers significant enhancements in application security and stability. It introduces comprehensive Server-Side Request Forgery (SSRF) protections for webhooks, reminders, and API integrations, alongside tightened access controls for managing tasks and email accounts. Numerous fixes address crashes and incorrect behaviors arising from malformed data inputs, while critical bugs, such as duplicate email sending, IMAP data corruption, and a complete breakage of chat functionality, have also been resolved. --- Этот выпуск содержит значительные улучшения в безопасности и стабильности приложения. Он включает комплексные средства защиты от подделки запросов на стороне сервера (SSRF) для веб-перехватчиков, напоминаний и интеграций API, а также усиленный контроль доступа для управления задачами и учетными записями электронной почты. Многочисленные исправления устраняют сбои и некорректное поведение, возникающие из-за неправильных входных данных, а также решают критические ошибки, такие как дублирование отправки электронной почты, повреждение данных IMAP и полная неработоспособность функции чата.

Fixes #5082 - fix(email): atomically claim scheduled emails before sending (#5110) _scheduled_poll_once selected rows WHERE status='pending' and only wrote status='sent'/'failed' after the SMTP send and IMAP append completed - no atomic claim in between. Two overlapping callers (the in-process 30s poller and an externally cron/systemd-driven 'odysseus-mail poll-scheduled', or the CLI run manually) can both SELECT the same pending row before either UPDATEs it, and both send it. _start_poller's own docstring already names this exact risk ('avoid two copies of _scheduled_poll_once racing on the same SQLite') but nothing in the code enforced it - it was advisory only. Add an atomic per-row claim: UPDATE ... SET status='sending' WHERE id=? AND status='pending', proceeding only when rowcount == 1. The loser of the race sees rowcount == 0 and skips the row instead of sending a duplicate. Adds a regression test that drives two real threads through the real _scheduled_poll_once against a shared SQLite file, synchronized with a barrier and a widened send-path window, and asserts exactly one send fires. Reverting the fix makes the test fail reliably (5/5 runs); with the fix it passes reliably (5/5 runs).
