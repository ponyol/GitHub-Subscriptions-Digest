Главной новой функцией является подкоманда `tl build-images`, позволяющая локально создавать Docker-образы непосредственно из определений приложений Tensorlake, с поддержкой шаблонов и опциональной загрузки в реестры. Это обновление также включает значительную архитектурную переработку, перенося пользовательский интерфейс командной строки (CLI) на Rust, в то время как скрипты Python теперь служат производителями NDJSON для повышения эффективности и кроссплатформенной упаковки. Кроме того, были внесены исправления для сборки и упаковки, особенно для платформ `aarch64` и macOS, что обеспечивает более широкую совместимость и более плавные выпуски.

- Add new build-image subcommand (#558) Adds a new CLI command that builds Docker images directly from Tensorlake application definitions, without requiring a full cloud deployment. ## What it does - tl build-images <app.py> loads the application file, discovers all Image definitions, and builds them locally using the Docker daemon via Bollard - Optionally push images to a registry with --push and --repository - --template <dockerfile.j2> supports MiniJinja-templated Dockerfiles, with the generated Tensorlake Dockerfile injected as {{ tensorlake_image }} - --stage sets the AS <stage> alias on the FROM line (useful for multi-stage template builds) - Validates Docker is reachable before starting; streams build output to stderr in real time ### New template flag This flag is new in the rust implementation. It allows to create more complex images based on the image definition in the code. For example, you can use it to install a specific system package that's not relevant for the functions to know about. You can also build multi-stage images by adding additional stages to the template that the functions don't care about. ## Architecture The command follows the same pattern as tl deploy: a Python wrapper script (tensorlake-build-images) is spawned by the Rust CLI. The Python side loads the user's application file and emits image definitions as NDJSON on stdout; the Rust side owns all Docker operations (build, tag, push). Image context creation (Dockerfile generation + tar.gz archive) was moved from Python into the cloud-sdk crate (Image::create_context_archive, Image::dockerfile_content) so it is the single source of truth shared by both the CLI builder and the cloud deployment path.
