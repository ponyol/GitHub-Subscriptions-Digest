If a subsequent request comes from a function with a different signature, the scheduler tries to extract params that don't exist on that function and hits an `AssertionError`. For example, the pool gets initialized with `_chat_completions_get_request_resources(messages, model, model_kwargs)`. When a `vision(prompt, image, model, model_kwargs)` request goes through `_get_request_resources`, it tries to extract `messages` from vision's signature and blows up. The fix adds a guard in `_get_request_resources` that checks for signature compatibility before extracting params. When there's a mismatch, it falls back to a conservative default estimate (1 per resource). This is fine because the scheduler self-corrects after each API call via actual rate-limit headers. In the future we should probably rework how `get_request_resources` is associated with pools. Ideally each function would register its own resource estimator rather than having a single estimator per pool that assumes all functions share the same signature. But for now this patch unblocks the common case without a redesign.
