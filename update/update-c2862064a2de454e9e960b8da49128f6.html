This release introduces key stability and security enhancements. It addresses critical bugs, including fixing vector-indexed nodes disappearing from KNN results after updates and preventing defragmentation from stalling write operations. Additionally, it improves Docker image security by installing `su-exec` and corrects version parsing in release workflows. --- Этот выпуск представляет собой ключевые улучшения стабильности и безопасности. Кроме того, повышена безопасность образов Docker за счет установки `su-exec` и исправлен парсинг версий в процессах выпуска.

Any write to a vector-indexed node re-indexes it as a RediSearch REPLACE, which mints a new docId and appends a new vector; the previous vector must be removed from the HNSW graph but never was, because the Index_HasVecSim spec flag was never set for indexes created through the low-level C API. Node deletion leaked the vector too, since the LLAPI delete (RediSearch_DeleteDocument) only dropped the doc-table entry. The orphaned vectors (docIds that no longer resolve) shadow live entries in KNN, so a node "disappears" from results at small k - e.g. k=1 returns nothing after any update, and a node inserted where a deleted one used to be is unfindable. The fix lives in the vendored RediSearch (FalkorDB/RediSearch#23): set Index_HasVecSim on vector-field creation, remove vectors in RediSearch_DeleteDocument, and cache the VecSim index pointer on the field to avoid a per-operation key allocation and keysDict lookup. tests/flow/test_vecsim.py: - test08: re-SET (same value / different value / unrelated property) keeps the node findable at k=1. - test09: deleting a node removes its vector, so a new node at the same coordinates is not shadowed. Both tests fail against the pre-fix submodule and pass with the bump. - fix(defrag): don't stall or orphan writes under active defrag (#2191) * fix(defrag): don't stall or orphan writes under active defrag Active defrag (#2175) runs on the Redis main thread and takes the graph write election before scanning. Under write load this caused two problems, reported as unusable writes on the edge docker image: 1. Main-thread freeze. Defrag waited up to 50ms PER lock (write election + rwlock = up to 100ms), blocking the event loop. Replace the per-lock timeouts with a single DEFRAG_BUDGET_MS (50ms) budget shared across the election wait, the rwlock wait and the scan, so a defrag step never blocks the main thread longer than the budget while still making progress (a non-blocking timeout=0 was rejected: it starves defrag under read load). Also poll a monotonic deadline in the election wait instead of decrementing an assumed sleep, so the timeout stays honest if nanosleep wakes on a signal. 2. Orphaned write / permanent hang. A write delegated to the write queue while defrag transiently owned the election was never drained (defrag runs on the main thread and does not drain the queue), so the blocked client hung forever while the server stayed responsive. Defrag now hands the queue back to a writer thread via Graph_DrainWriteQueue after releasing the election; the writer path is unchanged. Add testDefragWriteHang: streams a CREATE load while aggressive defrag churns the same graph, asserting the load finishes (no hang) with every write landed exactly once.
