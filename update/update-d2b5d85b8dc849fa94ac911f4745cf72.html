Суммаризация (на русском)

This update introduces extensive optimizations for GPU kernels, notably for SM100 and AMD architectures, featuring advanced FP4/MXFP8/NVFP4 quantization, migration to TileTensor, and a significant refactor of the `sm100_structured` directory to enhance grouped GEMM operations. Model support is expanded with new FP4/FP8 quantized DeepSeek-R1 and Qwen3-VL models, along with DeepSeek V3.2 MoE layers, while the MAX framework now includes an eager MO graph interpreter and improved input buffer synchronization for overlap scheduling. Additionally, the Mojo standard library sees substantial refactoring for type management and clarity, complemented by enhancements to development tooling for cross-compilation and `bazel` integration. --- **Russian translation:** Это обновление включает обширные оптимизации для ядер GPU, в частности для архитектур SM100 и AMD, с продвинутой квантизацией FP4/MXFP8/NVFP4, миграцией на TileTensor и значительной реорганизацией каталога `sm100_structured` для улучшения операций группированного GEMM. Расширена поддержка моделей за счет добавления новых квантованных моделей DeepSeek-R1 и Qwen3-VL (FP4/FP8), а также слоев MoE для DeepSeek V3.2, при этом фреймворк MAX теперь содержит интерпретатор графов MO для немедленного выполнения и улучшенную синхронизацию входных буферов для планирования с перекрытием. Кроме того, стандартная библиотека Mojo прошла существенный рефакторинг для управления типами и повышения ясности, что дополнено улучшениями в инструментах разработки для кросс-компиляции и интеграции с `bazel`.

This PR opts out of driver's auto sync for pinned model inputs. This allows `tensor.to_numpy()` to no longer cause the cpu to block until all work on the stream is complete. As `disable_auto_sync()` is unimplemented for non pinned memory, we have to guard each call to `disable_auto_sync()` based on whether it is pinned. If we omit this, we get a rather terse error message from the driver: - `RuntimeError: Unimplemented` Perhaps a future pr could modify this api but I think that is out of scope for this PR. Eg: this could be a no-op for pageable memory. It is safe to opt out because we call `.to_numpy()` right after the buffer is created so no previously issued work could be inflight that could mutate the buffer. We do not opt out for the graph output pinned buffer. Hence we still block on that call to `.to_numpy()`. This is needed for overlap scheduling.
