Суммаризация (на русском)

Это обновление добавляет полную поддержку процессоров Granite Rapids с новыми CPU шаблонами, конфигурациями тестов и документацией. Оно исправляет критические ошибки, связанные с открытием FIFO файлов и шаблонами CPU для Granite Rapids на хостах с ядром 5.10, а также улучшает функциональность VSOCK, устраняя состояние гонки при создании/восстановлении снапшотов путем сохранения последнего использованного локального порта. Кроме того, было обновлено множество зависимостей Rust.

Fixes: 74a51618038d ("doc(vsock): clarify vsock support on snapshot/restore") Signed-off-by: Takahiro Itazuri <itazur@amazon.com> - vsock: Save last used local port into snapshot Firecracker puts a VIRTIO_VSOCK_EVENT_TRANSPORT_RESET event into the event virtqueue and injects an interrupt during snapshot creation to tell the guest that it should close active connections. However, there is a race between the guest processing the event and the new connection requests from the host after snapshot restore. If such a race condition occurs, VSOCK_OP_REQUEST packet may be sent to an already established connection (i.e. a tuple of guest CID, guest port, host CID and host port). In that case, no VSOCK_OP_RESPONSE may not be responded, and if the client does not configure a timeout, it may end up waiting indefinitely (because Firecracker applies its connection request timeout only reactively). To minimize the chance of host port collisions, save the last allocated local port into a snapshot and resume allocation from the next port. NOTE: We don't bump up the snapshot version because we've already done it when migrating from bincode to bitcode [1] and both of them are to be released in the same Firecracker version. [1]: https://github.com/firecracker-microvm/firecracker/commit/37480d9cad246e5b6b004c41fe69e5914224d27e Signed-off-by: Takahiro Itazuri <itazur@amazon.com> - chore(vsock): Add comment for local port range Firecracker uses the range [1 << 30, 1 << 31) for local port allocation, which results in some seemingly tricky bit manipulation at allocation time. This dates back to when the vsock implementation was first introduced. I'm not aware of the discussions that took place at the time, but ensuring that the most significant bits always start with 01 does make some sense from a debugging and identification standpoint. In addition, it provides 1 billion available ports that should be enough to avoid port collisions. There's no reason to change this behavior at the moment; however, the bit manipulation would probably look a bit weird to someone seeing it for the first time (like me!). So add some comments about that opportunistically. Signed-off-by: Takahiro Itazuri <itazur@amazon.com> - refactor(vsock): Send reset event before saving transport state Firecracker puts a VIRTIO_VSOCK_EVENT_RESET_TRANSPORT event into the event virtqueue during snapshot creation and injects an interrupt to notify the guest driver. Previously, this was done after saving the transport state. That should be fine since we save the guest memory containing the virtqueue and injects an interrupt on resume. However, we introduced prepare_save() on virtio device that is called to inject an interrupt before saving the transport state, as the transport state holds the interrupt status (see [1]). There is no reason not to do the reset event injection in prepare_save(). Although that should eliminate the need of kick() on resume, triggering the interrupt multiple times should not cause any farm, so leave kick() as it is.
