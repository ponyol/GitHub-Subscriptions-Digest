- gptel: Fix parent preset handling * gptel.el (gptel--apply-preset): The fix for anonymous parent presets in e505a9d6 undid the change in c3d5d7f to preserve the value of the variable `gptel--preset' when applying a preset with parents. Fix `gptel--apply-preset' so that both properties are preserved: - Applying anonymous parent presets doesn't throw an error - `gptel--preset' is set only to the preset being applied. As a reminder, the second property is essential when applying presets in a oneshot manner -- otherwise the parent preset is recorded as `gptel--preset'. * test: Add some unit tests for preset handling. - gptel: allow anonymous plist parents in gptel--apply-preset The cl-flet refactor in c3d5d7f758b wrapped the :parents loop in get-preset, which unconditionally calls gptel-get-preset to convert parents to anonymous plists. This throws for parents that are already anonymous plists. Fix (but preserve the spirit of c3d5d7f758b) by moving the to-spec dereferencing away from the `:parents` list, and instead applying it to the top-level preset in `gptel--apply-preset`. Also recursively apply parents _before_ the `gptel--preset` is set, so that at the end of the function, the `gptel--preset` is correctly set to the top-level preset. - gptel-anthropic: Guard against missing usage info in response * gptel-anthropic.el (gptel--anthropic-update-tokens): Under certain conditions (not clear), token usage information might be missing from the final "message_delta" block of the response. Default to 0 tokens for missing fields. In this case the missing token info is actually available in the "message_start" block at the start of the response, but it's not clear when or why this happens. (#1331) This needs to be investigated to accurately capture the Anthropic backend's token usage. - gptel-openai: Remove reasoning-model-p check * gptel-openai.el (gptel--request-data): Remove the reasoning-model-p check. This check is both wrongly named and no longer necessary, as far as we can tell. It's wrongly named because what it's actually checking for is (i) whether some OpenAI models need special treatment for use with the Completions API because they are fully supported only with the OpenAI Responses API, and (ii) excluding the temperature setting when using o* series models. OpenAI backends now use gptel-openai-responses, and OpenAI proxies like Openrouter handle the Completions API in full, even when using the o* models. So this check is no longer required. - README: update Github copilot endpoints docs * README.org (GitHub CopilotChat): Update configuration for Copilot. - gptel-openai-responses: Update temperature handling for o-models * gptel-openai-responses.el (gptel--request-data): Simplify the model-based special-case handling in this function. Only the o-series models need special treatment, as they don't support the temperature parameter.
