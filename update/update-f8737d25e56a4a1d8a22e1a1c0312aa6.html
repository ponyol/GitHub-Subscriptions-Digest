Суммаризация (на русском)

The update brings major enhancements to agent integrations, including the addition of the Hermes Agent and improvements to the Google Antigravity (agy) integration. It introduces environment variables for overriding agent executables and passing extra arguments (`SPECKIT_INTEGRATION_<KEY>_EXECUTABLE`, `SPECKIT_INTEGRATION_<KEY>_EXTRA_ARGS`). Workflows now expose a `{{ context.run_id }}` variable for runtime context, and post-execution hooks are more robust for LLM interaction. The release also features security prompts for URL-based extension installs, along with various bug fixes, dependency updates, and CLI refactoring. --- **Russian translation:** Это обновление значительно расширяет возможности интеграции агентов, включая добавление агента Hermes и улучшения интеграции Google Antigravity (agy). Введены переменные окружения (`SPECKIT_INTEGRATION_<KEY>_EXECUTABLE`, `SPECKIT_INTEGRATION_<KEY>_EXTRA_ARGS`) для переопределения исполняемых файлов агентов и передачи дополнительных аргументов. Рабочие процессы теперь предоставляют переменную `{{ context.run_id }}` для контекста выполнения, а пост-исполнительные хуки стали более надежными для взаимодействия с LLM. Релиз также включает запросы безопасности для установки расширений по URL, а также различные исправления ошибок, обновления зависимостей и рефакторинг CLI.

Surfaces the engine-assigned run id (the same 8-character hex string Spec Kit prints as `Run ID:` at the end of `workflow run`) as a workflow template variable so YAML authors can reference it from shell `run:`, command `input.args:`, switch `expression:`, and any other field that already evaluates `{{ ... }}` templates. ### Why The run id is the natural join key between a Spec Kit workflow run and downstream artifacts, telemetry, or per-run scratch state. Today the operator sees it in stdout but workflows themselves cannot reference it — there was no way to stamp a log line, name a scratch directory, or tag an artifact with the same id Spec Kit assigned. The three motivating use cases from the issue: 1. Telemetry / observability — stamp logs and events with the run id so external systems can join workflow runs to downstream artifacts. 2. Per-run scratch / isolation — interactive operator commands that need their own state directory under `/tmp/run-<id>/`. 3. Run-id in artifact metadata — stable join key from artifact back to the producing run. ### Implementation `StepContext.run_id` is already populated by `WorkflowEngine` in both `execute()` and `resume()`.
