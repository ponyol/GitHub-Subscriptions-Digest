Суммаризация (на русском)

This update significantly refactors the `cognee` platform, transitioning to v1.0 API endpoints like `remember`, `improve`, and `recall` while consolidating skill ingestion into a unified `cognee.remember` flow. It introduces enhanced agentic skill management, allowing for idempotent skill ingestion, search, and self-improvement. Alongside these feature changes, the update also brings substantial infrastructure improvements, including better resource cleanup, increased database capacity, configurable caching, and automatic detection of embedding dimensions for improved stability and performance. --- Это обновление значительно рефакторит платформу `cognee`, переходя на конечные точки API v1.0 (`remember`, `improve`, `recall`) и унифицируя процесс приёма навыков в единый поток `cognee.remember`. Введена улучшенная система агентного управления навыками, обеспечивающая идемпотентный приём, поиск и самосовершенствование. Кроме того, реализованы значительные инфраструктурные улучшения, включая эффективную очистку ресурсов, увеличенную ёмкость базы данных, настраиваемое кэширование и автоматическое определение размерности эмбеддингов, что повышает стабильность и производительность системы.

Every other embedder (fastembed `BAAI/bge-small-en-v1.5` → 384, OpenAI `text-embedding-3-small` → 1536, ollama/nomic-embed → 768, etc.) hit a `Vector(3072)` / actual-dim mismatch on first write into LanceDB: ``` pydantic.ValidationError: 1 validation error for LanceDataPoint[...] vector List should have at least 3072 items after validation, not 384 ``` This kills `extract_chunks_from_documents`, `add_data_points`, and `extract_graph_and_summarize` — they all share the same persistence path. Graph extraction itself succeeds (the LLM call returns nodes/edges fine); it's purely a downstream schema-mismatch on persistence. ## Approach - Default `embedding_dimensions` to `None` (was `3072`). - In `model_post_init`, when not explicitly set, look up: - **fastembed**: `TextEmbedding.list_supported_models()` (handles both `dim` and `embed_dim` registry schema variants). - **everything else (litellm-routed)**: `litellm.model_cost[model]['output_vector_size']`, trying full model key, the prefix-stripped key (`text-embedding-3-large`), and `provider/bare` (`openai/text-embedding-3-large`). - If still unresolvable, fall back to `3072` with a loud warning telling the user to set `EMBEDDING_DIMENSIONS` explicitly. This preserves the pre-fix behavior for users who already had working configs — the default `openai/text-embedding-3-large` still resolves to 3072 via litellm (verified in tests). - Explicit `EMBEDDING_DIMENSIONS` env always wins. ## Why auto-derive instead of fail-fast Failing fast on missing dimensions would be a regression for everyone using the OpenAI defaults today.
