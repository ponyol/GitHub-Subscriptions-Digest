- Multi-parameter application function calls (#502) Application function calls now support any number of positional and keyword arguments, with default argument values applied if some arguments are not passed. SDK run application functions which are part of SDK interface are updated with new backward compatible signature: ``` def run_local_application(application: Function | str, *args, **kwargs) -> Request: def run_remote_application(application: Function | str, *args, **kwargs) -> Request: ``` In remote mode the API client passes empty HTTP body to Server if application function is called without any parameters. If application function is called with a single position arg then the current approach is used where the arg is serialized into HTTP body and HTTP content type is the same as serialized arg content type. In all other cases multipart HTTP request is used with each arg serialized as a separate part in the request body. A parser with zero data copy and bytes.find() used for substring search is implemented for multipart request bodies. bytes.find() is more than 1000x faster than searching substrings in Python because it's fully implemented in C and uses fast substring search algorithms. These first two call modes (no parameters and one positional parameter) allow users to use non-multipart (simpler) curl commands. Field names in multipart mode are used to map body parts to application function parameters. If a field name is a number then it's an index of positional argument of the function. If a field name is not a number then it's name of a keyword argument of the function. The mapping logic is permissive, i.e. it ignores non- existent keyword arguments. This allows to simplify code changes for users. I.e. they can send a request with a new arg in it while the request not failing if it land on application function of previous version that doesn't have the arg added yet. Web frameworks typically ignore parts that are not consumed by user code too. For multypart and empty body calls to work no Server changes are required at the moment because Server just forwards the HTTP bodies with their content type to FE. FE also now supports mode (turned on using "message/http" content-type) where Server can forward full HTTP request to FE. In this case FE parses full HTTP request and its headers become available to it. These headers would be used in the future for future SDK features. For now we just leave this capability in FE to be able to not fail user requests once Server changes it behavior and starts forwarding full HTTP requests. I ran all integ tests both with current Server and Server that forwards full http request. All pass. I also added an FE test that uses HTTP request forwarding mode to call application function just to make sure that we don't regress on implementation of this feature while we're not using it on Server side. Added tests that check all these scenarios. All the commong new code is shared between local and remote runners. Also added missing test coverage for regular and application function calls that accept File objects as arguments and return File objects. - update readme - Add HTTP API documentation to README Document how to invoke applications via HTTP/curl including: - Basic invocation with request ID response - Checking request status - Getting results - SSE streaming - Sending files Co-Authored-By: Claude Opus 4.5 <noreply@anthropic.com> - Added chart extraction option (#501) - Durability: Encode function call sequence numbers and Awaitable tree hierarchy into function call (Awaitable) IDs (#494) This is required for durability/replayability feature. Durable Awaitable IDs are the same across different executions (allocations) of the same parent function call if the parent function call is deterministic, i.e. it creates the same awaitable trees in the same order each time it's executed. If this is not the case then the Awaitable IDs will differ between executions, which may lead to re-execution of some function calls even if their inputs are the same as in a previous execution. Server will be deciding if this is allowed or not. To produce a durable Awaitable ID, we compute it as a hash of: - parent_function_call_id in the tree - awaitable_sequence_number (unique per Awaitable created by an allocation). This ensures that any two Awaitables created by the same parent function call get different durable IDs even if the Awaitables are otherwise identical (i.e. two calls of the same function with same parameters). This also ensures that each durable ID is unique per each execution of parent function call. - Awaitable-specific metadata. This ensures that we detect changes in Awaitable tree nodes, i.e. change of called function name. - Deterministically ordered durable IDs of all immediate child Awaitables. This ensures that changes in the structure of the awaitable tree leads to different durable IDs of its nodes starting from root so it's easy to detect a drift on Server side just by comparing durable ID of root. We're deliberately not hashing entire awaitables to produce their durable IDs. This is because hashing entire awaitables is an expensive operation (i.e. hashing gigabytes of arbitrary user supplied objects which are function call parameters). This also results in better UX, i.e. this allows: - Seamless Schema Evolution: Users may want to change the schema of function parameters (e.g. add a new field with a default value to a pydantic model). - Use of non-deterministic functions: Users may want to use non-deterministic functions (e.g. functions that return current time or random values) inside otherwise deterministic function call trees. - To avoid "Serialization Flakiness": Strict equality checks on serialized data are fragile and can lead to false positive re-executions due to minor, non-semantic changes in serialization (e.g. different field ordering in protobufs, or insertion order in dicts). - To decouple Logic from Data. We adhere to a philosophy of being Strict on Control Flow but Lenient on Data. "The History is the Source of Truth." This PR also includes some simple rename/comment refactorings that clarifies semantic or variables/fields.
