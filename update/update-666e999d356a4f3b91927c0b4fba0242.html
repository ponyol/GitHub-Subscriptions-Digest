The product code is left intact. - [PXT-1094] Import RDBMS sources into Pixeltable tables (#1324) Adds pxt.io.import_sql(), which streams rows from any SQLAlchemy Selectable (a Table, a select() statement, or text(...).columns(...)) executed against a user-supplied Engine or Connection into a Pixeltable table. The same call covers create+insert (if_exists='error') and append into an existing table (if_exists='append'). replace is intentionally omitted, because create+insert is not atomic and a failed insert would leave the user with an empty replica of the source schema; callers wanting overwrite semantics should drop_table first and then call import_sql(..., if_exists='error'). All schema-side validation lives in import_sql() itself: unnamed or duplicate source columns, columns whose SQLAlchemy type does not map to a Pixeltable type (and is not resolved via schema_overrides), schema_overrides keys that do not appear in the source, computed-column collisions on append, type incompatibility between source and destination, and missing required destination columns. The reason for doing all of this preflight work in import_sql() is to keep SqlDataNode purely a runtime data path. By the time the plan is built the source is already known to be valid, so the node only has to build a slot mapping from source column names to row-builder slots and stream rows; nothing in the execution path has to re-derive or revalidate the schema. SqlDataNode lives in its own module (pixeltable/exec/sql_data_node.py) rather than in sql_node.py. The existing nodes in sql_node.py (SqlScanNode, SqlAggregationNode, SqlJoinNode, etc.) all push parts of a Pixeltable query plan down into the embedded Postgres against catalog-managed tables. SqlDataNode does the opposite: it reads from a foreign, user-supplied database and feeds those rows into the insert pipeline. Its output contract (output_exprs = row_builder.input_exprs, populates user-column slots by name, sets unmapped slots to None) mirrors InMemoryDataNode, which is the right analogue for streaming external rows into a table. Keeping it in sql_node.py would have suggested it participates in plan pushdown, which it does not. Planner.create_insert_plan now takes either rows or a sql_source (exactly one), and selects InMemoryDataNode or SqlDataNode accordingly.
