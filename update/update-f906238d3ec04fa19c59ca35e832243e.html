Суммаризация (на русском)

Это обновление значительно развивает язык Mojo, перестраивая дизайн итераторов для использования стиля Python с `StopIteration` для завершения и вводя новые API для рефлексии по полям структур во время компиляции. Оно также включает различные усовершенствования системы типов Mojo, такие как обработка `Origin` и специализация `Optional`, наряду с улучшениями преобразования функций и вывода типов. Кроме того, релиз повышает стабильность и производительность сборочной системы Bazel и ядер, решая проблемы аутентификации, улучшая надежность тестов и переходя на функции GPU с проверкой типов.

Mojo supports two different kinds of for-each iterators: many collections are capable of returning references to their elements, but some (e.g. integer ranges) need to compute or return copies of some existing value. Neither approach is right for all uses, but returning values is more general, and traits yet support computed origins in returned references. It isn't possible to overload methods on return type, so we used two different names for these cases: next and next_ref. This patch eliminates next_ref by using the recently added support for function subtyping, which allows a function returning a ref to convert to a function returning a T when T is copyable. This simplifies the language and cleans things up. MODULAR_ORIG_COMMIT_REV_ID: de08e152bf0c67bb8c99f65f8eab9bbd54fbaada - [mojo-lang] Switch `__next__` to throwing StopIteration This completes the migration of `Iterator` to Python-style design where `__next__` raises at the end of iteration instead of having a separate `__has_next__` method. In addition to being Pythonic, this is also easier to implement and use, more safe for clients, and can be slightly more efficient in some cases. Now that the mojo compiler's lowering of for-each loops can support a raising `__next__` method in iterators, take the next step and switch `Iterator` to requiring a raising next, and completely eliminate `__has_next__` from Mojo. Doing this requires reworking parameter for lowering a bit, introducing a new `paramfor_has_next` helper, but the biggest change is reworking all the testcases and iterators in the tree. I would like for this to be phase-in-able somehow, but I don't see a practical way to do so. We just have to accept this as a major breaking change for folks that have custom iterators unfortunately.
