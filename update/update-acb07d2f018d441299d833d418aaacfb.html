Суммаризация (на русском)

Это обновление вводит выделенный конечный автомат для `gptel-send` для надежной поддержки хуков до и после вызова инструмента, позволяя прерывать запросы на этих этапах. Оно также значительно повышает безопасность, ограничивая потенциально небезопасные файловые локальные переменные. Среди прочих ключевых улучшений — исправление сопоставления параметра температуры Gemini, устранение ошибок валидации ссылок и доработка сообщений об ошибках Curl, а также обновление деталей модели gpt-5.4.

- gptel-gemini: Fix Temperature parameter mapping * gptel-gemini.el (gptel--request-data): Ensure the Gemini backend respects temperature settings below 1.0. Previously, the code used (max gptel-temperature 1.0), which effectively ignored any user setting in the 0.0-0.9 range. Fixes #1312. - gptel-org: Fix bug in link validation This fixes the following failing unit tests: gptel-test-media-link-parsing-md-1 and -2 gptel-test-media-link-parsing-org-1 and -2 * gptel-org.el (gptel-org--validate-link): Fix logic bug in setting `mime-valid'. Alist `gptel--link-type-cache' was populated incorrectly: text files were marked as `("/foo/text.txt" . t)' and binary files as `("/foo/image.png" t . 10)'. The text file case was wrong (t instead of nil), and the image had a number as a side effect of the fact that `gptel--file-binary-p' passes the number returned by `string-match-p' (insted of t) if the file name matches a known file type like `.png'. * gptel-request.el (gptel-markdown--validate-link): Fix the identical issue in the markdown variant of the function. - gptel: Ensure safety of file local variables * gptel-request.el (gptel--system-message, gptel--num-messages-to-send): System message can be a function that will be evaluated when invoking `gptel-send', which is not safe when opening untrusted files. num-messages-to-send is less risky, but still safer not to use `always'. * gptel.el (gptel--bounds, gptel--tool-names, gptel--backend-name): Replace `always' with more specific predicate functions as well. - gptel: Don't transition FSM in gptel--handle-pre-tool * gptel.el (gptel--handle-pre-tool): Don't transition the FSM as part of this function. This is conceptually cleaner, as `gptel--handle-pre-tool' does only one thing now (run `gptel-pre-tool-call-functions') and can be called in more contexts if required. (gptel-send--handlers): Move the FSM transition here. * test: Update test for `gptel--handle-pre-tool'. - gptel-openai: Correct gpt-5.4 pricing and context window * gptel-openai.el (gptel--openai-models): Correct gpt-5.4 model pricing information and context window. (#1304) Source: https://developers.openai.com/api/docs/models/compare - gptel-request: Linting * gptel-request.el (gptel-curl--sentinel): Use the right INFO plist variable name. - gptel: Inspect the correct FSM when tool calls are pending * gptel.el (gptel--inspect-fsm): When waiting for tool call confirmation, the Curl request has effectively ended, so we cannot find the active request FSM in `gptel--request-alist'. Prefer to inspect `gptel--fsm-last' instead, which should be updated in gptel-send's state handlers. - gptel: Introduce a separate gptel-send transition table * gptel.el (gptel-send--transitions): Until now, `gptel-send' and `gptel-request' have used the same transition table, differing only in their FSM state handlers. But `gptel-send' now supports pre- and post-tool-call hooks that `gptel-request' doesn't. These tool call hooks can drastically change the flow of the request, including stopping the request immediately. `gptel-send' thus needs dedicated FSM states and transitions. (This is unfortunate, but we pushed the reuse far enough. It's time.) The primary difference between the two is a new state TPRE where the pre-tool-call hook runs and can transition the FSM to ERRS. (gptel-send--handlers): Move `gptel--handle-pre-tool' to TPRE, its own state. (gptel--handle-pre-tool): Transition the FSM after (not) running `gptel-pre-tool-call-functions'. It must happen after the post-tool-call hook runs. * gptel.el (gptel--handle-pre-tool, gptel--handle-post-tool): Don't hard-code the transition to the ERRS state, and improve the error reporting when the request is stopped. Per the design of the FSM, state handlers should never explicitly specify the next state. That should be determined by the predicates based on data in the FSM INFO plist. As of this and earlier commits, aborting requests from `gptel-pre-tool-call-functions' is non-functional. This will be addressed next. - gptel: Improve messaging on Curl failure * gptel.el (gptel--handle-error): This function displays errors in two ways: in the status-line of gptel buffers, and via message. The value of STATUS can be any string, and not just a HTTP code as was previously assumed. * gptel-request.el (gptel-curl--stream-cleanup, gptel-curl--sentinel): Improve Curl failure messaging.
