Companion to nori-skillsets #538, which stopped the *symptoms* (global-config clobber + phantom "conflicting files" block, released in 0.31.0). This PR stops the CLI from **creating** the orphaned state in the first place. **The bug.** In `chatwidget/pickers.rs`, both `handle_switch_skillset_command()` and `handle_switch_skillset_command_with_name()` derived `--install-dir` as `if is_in_worktree || skillset_per_session { Some(self.config.cwd) } else { None }`. When `skillset_per_session` was on but **no worktree existed** (auto-worktree off, blocked on a dirty tree / non-repo, or the user declined the ask), `config.cwd` is the **repo root** — so `nori-skillsets` installed `.nori-managed` markers + manifests into the project tree and orphaned them. (When auto-worktree *does* fire, `config.cwd` is already the `.worktrees/<name>` path, so that path was fine.) ## What changed - **`session_skillset_install_dir(cwd)`** (new, in `nori/skillset_picker.rs`): returns `Some(cwd)` only when `cwd` is a worktree, else `None` (home install). `skillset_per_session` no longer forces a non-worktree cwd. Both switch call sites delegate to it (net-negative: also drops a `NoriConfig::load()` disk read per call). - **Deferred-spawn fix (blocker caught in self-review):** routing the no-worktree case to `InstallSkillset` exposed a latent asymmetry — `SkillsetInstallResult` never resolved the deferred agent spawn (only `SkillsetSwitchResult` did), so a per-session startup that home-installs would **hang with no agent**. Extracted `take_deferred_spawn()` + `on_skillset_applied()` so Install / Switch / Dismissed share one guard and can't drift again. - **Picker subtitle:** when per-session is on but there's no worktree, the picker now says the install is global instead of silently doing a home install. - Updated `tui/docs.md`. ## Known limitation (deliberate) Worktree detection stays path-based (`extract_worktree_name`, matches the `.worktrees/<name>` layout auto-worktree creates — the supported per-session mechanism). A hand-made `git worktree add ../foo` outside `.worktrees/` is not recognized and falls back to the home install. Previously that niche combo "worked" only via the same buggy `|| skillset_per_session` clause. `system_info::is_git_worktree()` (a git subprocess) could detect all linked worktrees if we decide that case matters; left out here to keep the helper pure/testable and the fix minimal. ## Test Plan - [x] `cargo test -p nori-tui` (1392 passed) — incl. new `install_dir_*`, `take_deferred_spawn_*`, and global-install-subtitle tests - [x] `cargo build --bin nori && cargo test -p tui-pty-e2e` (only the 3 pre-existing network-dependent `cloud_mode` tests fail; identical on untouched base) - [x] `just fmt` + `just fix -p nori-tui` clean - [x] Closed the loop: launched the built `nori` under ElizACP via tmux — renders, accepts input, prompt returns, no panic Share Nori with your team: https://www.npmjs.com/package/nori-skillsets
