- fix(tui,acp): keep loop-count mode alive through transient API errors (#516) ## Summary 🤖 Generated with [Nori](https://noriagentic.com/) Fixes the bug in `~/code/nori/BUG_REPORT.md`: loop-count mode silently stopped after an iteration hit a **transient** API error (Anthropic `529`/overloaded, rate limit). - **Root cause (verified in code):** `on_error()` unconditionally called `cancel_loop()`, so *any* error event permanently disarmed the loop. On a prompt failure the ACP backend emits both an `EventMsg::Error` **and** a `PromptCompleted{Cancelled}`; the error cancelled the loop, then the completion's `on_task_complete` found it disarmed and never re-fired. Long iterations make many model round-trips and are nearly certain to hit one transient error → loop dies. Short ones don't → loop fine. That matches the report's duration-correlation exactly. - **Fix — survive transient errors, cancel only on fatal ones:** added `retryable: bool` (`#[serde(default)]`) to `codex-protocol`'s `ErrorEvent`; new `AcpErrorCategory::is_retryable()` (true only for `ApiServerError`/`QuotaExceeded`); `send_prompt_error` sets the flag from the category (other producers — agent exit, generic op errors, compact/goal — are fatal). The TUI's `on_error(message, retryable)` now calls `cancel_loop()` only when `!retryable`, and the existing `PromptCompleted`→`on_task_complete` path re-fires the next iteration. - **Categorizer gap:** `categorize_acp_error` now classifies a bare `529` → `ApiServerError` and `rate_limit_error` (underscore) → `QuotaExceeded`, so the user's actual reported strings land in retryable buckets instead of `Unknown` (which would still have cancelled the loop). - **Observability** (the report's secondary "undebuggable" finding): added tracing at `cancel_loop`, `send_prompt_error` (category + retryable + raw error), and `on_error`. - **Docs:** corrected `nori-rs/tui/docs.md` (which wrongly said the loop cancels on *any* error) and `nori-rs/acp/docs.md` (added retryable column + new patterns + the `ErrorEvent.retryable` plumbing). I **deviated from the report's recommendation #2** (decouple `cancel_loop` from `on_error` entirely): because `PromptCompleted` always fires on failure, never cancelling would make a *fatal* error (bad auth) re-fire the loop and burn remaining iterations. Distinguishing retryable vs fatal is the correct fix. ## Known limitation (pre-existing, not introduced here) `EventMsg::Error` and `PromptCompleted` reach the TUI on two independent channels with no ordering guarantee. In the rare case `PromptCompleted` is processed first, the queued `LoopIteration` rebuilds the widget and restores loop state, so a *fatal* error processed afterward can fail to stop the loop. This behaves **identically** in the old code (which also cancelled the now-discarded widget), so it's not a regression. In practice the backend emits `Error` before `PromptCompleted`, so the common path is correct. A proper fix (unifying the two events onto one ordered channel, or carrying the error in the completion) is a larger refactor left as follow-up. Per-iteration backoff for slow-clearing `QuotaExceeded` limits is another sensible follow-up. ## Test Plan - [x] `cargo test -p nori-acp` — categorizer (`529`/`rate_limit_error`) + `is_retryable` per-variant coverage (551 + others, all pass) - [x] `cargo test -p nori-tui` — new `part10.rs` tests drive the real `handle_codex_event` seam: loop survives a retryable error and re-fires; stops on a fatal error (1342 pass) - [x] `cargo test --workspace` — full suite, 2765 tests, 0 failures - [x] `cargo build --bin nori && cargo test -p tui-pty-e2e` — all pass - [x] `just fmt` + `just fix` clean - [x] End-to-end TUI drive (ElizACP via tmux): launches, renders `›`, accepts input, prompt returns Share Nori with your team: https://www.npmjs.com/package/nori-skillsets - perf(build): set dev profile to line-tables-only debug info (#515) ## Summary Sets `profile.dev.debug = "line-tables-only"` in `nori-rs/Cargo.toml`. This keeps `file:line` info in backtraces while dropping the full DWARF that makes the final link of the `nori` binary memory-bound on low-RAM machines. ## Why While benchmarking clean `nori` builds across cargo/rustc/linker configurations, the dominant cost was **not** the linker choice (mold/lld/bfd are all within run-to-run noise). It was the debug-info footprint. On a RAM-constrained machine (no swap, `target/` on overlayfs), the default `debuginfo=2` makes the final link mmap huge DWARF inputs across ~600 crates. Under memory pressure the kernel evicts and re-reads those pages from disk, so the linker sits in disk-sleep reading tens of GB. A clean default-profile debug build **never completed in 35+ min**. Measured clean build of the `nori` bin by debug-info level (same machine, mold): | debug setting | clean build | notes | |---|---|---| | `debuginfo=2` (default) | did not complete (>35 min) | link thrash, ~70 GB of reads | | `"line-tables-only"` | ~9 min | no thrash, keeps backtrace line numbers | | `0` (none) | ~5 min | no thrash, no line numbers | `"line-tables-only"` is the sweet spot: it removes the thrash while preserving the `file:line` data that makes panic backtraces useful during development. ## Scope - Only `profile.dev` is affected. `profile.release`, `profile.test`, and `profile.ci-test` are unchanged. - `debug = "line-tables-only"` is the explicit string form — note `debug = 1` maps to `"limited"`, which is a different (larger) level. ## Test plan - [x] `cargo metadata --no-deps` parses the manifest cleanly - [ ] `cargo build` on a dev machine still produces usable backtraces with `file:line` Co-authored-by: Cliff <clifford@tilework.tech> Co-authored-by: Nori <contact@tilework.tech>
