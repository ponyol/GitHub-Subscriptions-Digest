Суммаризация (на русском)

Это обновление добавляет поддержку загрузки моделей ONNX Runtime из "пакетов моделей", которые объединяют несколько вариантов сборки. При загрузке ONNX Runtime может автоматически выбрать оптимальный вариант на основе оборудования, или пользователи могут явно указать его через обновленные API на C, C++ и Python. Кроме того, добавлен новый механизм разрешения путей (`ResolvePath`) для корректной интерпретации файловых путей в конфигурациях, основанных на пакетах.

- Load models from ONNX Runtime model packages (#2227) Adds support for loading a model from an ONNX Runtime *model package* in addition to the existing flat directory layout. A package bundles multiple build variants of the same model and lets ONNX Runtime select the variant matching the local hardware (and any execution provider hints) at load time. ## Public API * C: `OgaCreateConfig` / `OgaCreateModel` continue to work on flat directories. When given a model package they auto-detect the execution provider; an ambiguous package returns a clear error directing the caller to the new `OgaCreateConfigFromPackage` / `OgaCreateModelFromPackage` entry points, which take an explicit ep argument and require the path to be a model package. * C++: a two-argument `OgaConfig::Create(path, ep)` / `OgaModel::Create(path, ep)` overload routes through the `FromPackage` entry points. * Python: `og.Model(path)` / `og.Config(path)` handle both flat directories and packages; an `ep=` keyword selects a variant. The variant's `genai_config.json` remains the sole source of truth for the providers and provider options used at session creation time. The genai loader does not inject anything based on the package metadata. ## Single-component packages The genai loader expects exactly one component per package. The component can be named anything; the loader takes whatever name ORT reports. Multi-component packages return a clear error. ## Path resolution `Config` gains a `package_root` field (empty when not loaded from a package) and a `ResolvePath()` helper that interprets path-shaped strings from `genai_config.json`: | Form | Resolution | | --- | --- | | empty | `config_path` (variant directory) | | `package:<relative>` | joined with `package_root` (errors when no package root is set) | | anything else | joined with `config_path` | A new optional `model.tokenizer_dir` field uses this resolver. The existing `model.vision.config_filename` and `model.speech.config_filename` fields go through it too, including when they fall back to their default basenames. ## Tests + fixtures * New `test/model_package_test.cpp` covers package detection, single/explicit/ambiguous EP variant selection, `ResolvePath` scheme handling, package-only contract of the `FromPackage` C entry points, and rejection of an ep argument on a flat directory. * Two tiny hand-authored fixtures under `test/test_models/` (`tiny-cpu.ortpackage`, `tiny-ambiguous.ortpackage`) with placeholder `.onnx` bytes; no real model files are checked in. ## Docs `docs/model_package.md` walks through the package layout, the `tokenizer_dir` field, the path scheme, and the public API surface. --------- Co-authored-by: jambayk <jambayk@microsoft.com> Co-authored-by: Copilot <223556219+Copilot@users.noreply.github.com>
