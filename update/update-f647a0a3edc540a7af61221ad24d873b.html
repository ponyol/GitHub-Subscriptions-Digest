- Merge pull request #309 from Jwenqiang/fix/webhook-panic-crash fix: prevent process crash when webhook fires for a deleted user - fix: prevent process crash when webhook fires for a deleted user Two related issues caused wuzapi to crash with SIGSEGV when a WhatsApp event fired for a userID whose HTTP client had been removed: 1. Nil HTTP client deref in helpers.go. callHookWithHmac and callHookFileWithHmac call clientManager.GetHTTPClient(userID) and immediately use the returned client. When the user has been deleted via DELETE /admin/users/{id}/full but whatsmeow still has an in-flight event for that user, the client is nil and client.R().Post() panics. 2. Bare goroutines without recover in wmiau.go. sendEventWithWebHook spawns sendToGlobalWebHook and sendToGlobalRabbit as plain 'go fn(...)'. sendToUserWebHookWithHmac spawns callHookWithHmac the same way. None have defer recover, so any panic inside these goroutines (including the nil deref above) crashes the whole process via Go runtime, not just the one delivery. Fix: - helpers.go: nil-check client immediately after GetHTTPClient and log+return / log+error if nil. Stops the SIGSEGV at the source. - wmiau.go: add safeGo(name, fn) wrapper that recovers panics with zerolog ERROR + debug.Stack(). Route the three at-risk goroutines through it. Future nil derefs in fire-and-forget delivery paths now fail one delivery instead of killing the process. Observed in production 2026-05-25 before fix: 13 panics in ~10 minutes, RestartCount climbed to 154, restart storm caused WhatsApp to demote a companion device, losing 65 hours of inbound messages for that account.
