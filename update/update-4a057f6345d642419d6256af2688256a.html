Суммаризация (на русском)

This update introduces a unified configuration system and resolves a critical divergence in Unicode string handling between SQL and Python paths, ensuring consistent behavior. It also significantly improves error messages for incorrect User-Defined Function calls and adds functionality to export data from FastAPI routes to external SQL databases. Further enhancements include improved retry mechanisms for table operations, along with various formatting fixes and multimedia processing improvements. --- Это обновление представляет унифицированную систему конфигурации и устраняет критическое расхождение в обработке строк Unicode между путями SQL и Python, обеспечивая согласованное поведение. Оно также значительно улучшает сообщения об ошибках для некорректных вызовов пользовательских функций (UDF) и добавляет возможность экспорта данных из маршрутов FastAPI во внешние базы данных SQL. Дополнительные улучшения включают усовершенствованные механизмы повторных попыток для операций с таблицами, а также различные исправления форматирования и улучшения обработки мультимедиа.

Under that configuration, Postgres upper, lower, and character-class regex degrade to ASCII-only handling, while Python's str.upper, str.lower, str.capitalize, and the in operator all do Unicode case folding. The consequence was that the same Pixeltable expression could produce different answers depending on whether the planner pushed it down to SQL or evaluated it in Python. upper on lowercase accented e returned the accented e on the SQL path but the uppercased E on the Python path. Case-insensitive contains for an uppercase accented needle silently missed rows on the SQL path that Python matched. A where filter like where(upper(t.s) == 'CAFÉ') returned zero rows, while the Python-forced equivalent returned one. This PR switches the database locale to C.UTF-8 (and .UTF-8 on Windows, where UCRT rejects C.UTF-8). That gives Postgres the same per-codepoint case folding that Python uses, so SQL and Python paths now agree on Unicode input in upper, lower, capitalize, contains with case=False, and upper-based where predicates. This PR also adds three tests pinning down the new behavior. The first iterates upper, lower, and capitalize over a set of Unicode strings and asserts SQL and Python paths match each other and match Python semantics. The second covers case-insensitive contains and an upper-based where filter. The third shows a computed column materialized at insert time agrees with a live SQL-pushed upper, so where(upper(t.s) == t.upper_s) is a tautology. One known limitation: libc case folding is strictly 1:1, so length-changing conversions like the German sharp s expanding to SS, or the Greek final sigma, are not handled on the SQL path. A full fix would require an ICU-enabled Postgres build.
