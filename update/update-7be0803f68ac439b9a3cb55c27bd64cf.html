On a large project, tsserver can take longer than that just to resolve the project graph before it even creates the first progress token, so the first cross-file reference query can race a project that is still loading. That ambiguity cannot be resolved from client-observable signals alone, so this makes the grace an ls_specific_settings knob (`indexing_start_grace`), the same way indexing_timeout and server_ready_timeout already are, and raises the default from 2.0s to 5.0s. Fixes #1724 - Retry LSP ContentModified (-32801) errors instead of failing hard Per the LSP spec, ContentModified means the server discarded a stale, in-flight computation because the workspace changed underneath it, not that the request itself is invalid, so a well-behaved client is expected to retry. LanguageServerInterface.send_request previously converted any such response straight into a hard SolidLSPException, with no retry, for every language server. This was flaking test_find_symbol[rust_add_function] on windows-latest: rust-analyzer returns ContentModified for hover requests cancelled by concurrent indexing (its internal retry set does not cover hover), and nothing on the client side retried it. send_request now retries ContentModified responses a bounded number of times with a short delay before giving up. This is generic to the base request path, so it applies to every language server, not just rust-analyzer. RequestCancelled (-32800) is left alone since the LSP spec defines it as client-initiated.
