Each callback independently throttles at 1 event/sec, so after N retries, every download progress tick generates N events instead of 1. After an hour of failures (~60 retry cycles), this produces ~60 `NodeDownloadProgress` events/sec, overwhelming the master, delaying heartbeats, and causing the node to time itself out. ### The callback accumulation cycle 1. `_start_download_task()` calls `shard_downloader.on_progress(callback)` which **appends** to a list 2. Download fails → `DownloadFailed` status set, but old callback stays in the list 3. 60s later: `_emit_existing_download_progress()` scans disk → resets status to `DownloadPending` 4. Worker sends new `StartDownload` → coordinator accepts (guard didn't check `DownloadFailed`) 5. `_start_download_task()` appends **another** callback 6.
