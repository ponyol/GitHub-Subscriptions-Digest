[MP][DAX] coalesce DAX L2 load path : per-device batching, copies outside the adapter lock (#4010) * dax: coalesce L2 load path — batch per device, copy outside the adapter lock, parallel sub-batches _execute_load_task previously copied a request's chunks one at a time: each chunk went through load_many_into() with a batch of one (paying the full slot-reservation cycle per chunk), all copies ran sequentially on a single load worker, and the adapter-global _device_lock was held across the entire batch, serializing concurrent requests' loads against each other. This change: - groups the batch's keys per device under _device_lock (dict lookups only), releasing the lock before any data movement — per-device cores already take their own reservation locks; - issues real per-device batches to load_many_into(), amortizing the reservation cycle; - splits groups into ~0.5 GiB sub-batches copied via an inline thread pool; ctypes.memmove releases the GIL, so the copies overlap. A/B measured on CXL devdax (identical setup: one lane, 6 x 32 GiB devices, 8 x 43k-char Qwen2.5-32B prompts, concurrency 4, reuse after L1 clear): reuse mean TTFT 5683 ms -> 3307 ms (1.72x) reuse p99 TTFT 7116 ms -> 4727 ms (1.51x) prefetch p50 (44 chunks, 2.75 GiB) ~2040 -> ~1550 ms prefetch worst 2811 ms -> 1630 ms fill TTFT unchanged (load-path-only change) The stock tail (2.7-2.8 s prefetches) is requests queueing behind the adapter-global lock while another batch copies; removing that serialization is the dominant win and grows with MP-server concurrency. Raw medium bandwidth is 5.3 GB/s single-thread / 23 GB/s at 8 threads (GIL-free memcpy); the remaining gap is dominated by per-request L1 staging-buffer allocation above this adapter, left as follow-up.
