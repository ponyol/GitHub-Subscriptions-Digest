Суммаризация (на русском)

Ключевые изменения в этом обновлении сосредоточены на улучшении управления контекстом и надежности. Новая опциональная функция позволяет проводить сжатие контекста прямо посреди хода диалога, динамически уменьшая его во время длительных взаимодействий, чтобы предотвратить превышение лимитов модели. Оценка размера контекста была значительно откалибрована с использованием реальных данных о потреблении провайдера и улучшенным взвешиванием CJK-токенов, что привело к более точному пониманию контекста. Операции файловой системы для вывода инструментов теперь атомарны, что предотвращает повреждение данных при прерванных записях, а исправление устраняет проблемы с симлинками `resolv.conf` в WSL.

A process killed mid-write (terminal closed -> SIGHUP, or a crash) could leave an existing file truncated or destroyed. Add fs::atomic_write: write to a temp file in the same directory, then rename(2) over the target. rename is atomic, so a reader or an interrupted process only ever observes the complete old or complete new file. Original permissions are preserved, and symlinks are written through to their target instead of being clobbered. No fsync: atomicity comes from rename alone; fsync would only add power-loss durability at ~20-50x the per-write cost, which is out of scope for this failure mode. - fix(session): keep recent messages when keep_recent exceeds history size Extract the compaction cut-point selection into a pure, testable `select_compaction_cut`. Its loop initialized `cut_idx` to `messages.len()`, so when keep_recent was larger than the sum of per-message estimates the threshold never fired and the whole history was summarized, keeping nothing recent. The usage-calibrated compaction gate makes this reachable: the real context can exceed the budget (system prompt, context files) while the messages themselves stay small. Initialize to 0 instead, so an oversized `keep_recent` falls through to the existing "entire context is recent" path. The selection stays in the per-message estimate scale on purpose: it is a relative comparison among messages, so a uniform estimator bias cancels, calibration only matters for the absolute total. - feat(session): calibrate context-size accounting against provider usage `total_estimated_tokens` summed a per-message heuristic estimate over the whole history, so the estimator's error accumulated across every message and never accounted for the system prompt or context files at all. Anchor context size to the provider's reported usage instead. After each completed turn, `set_calibration` records the real input + output tokens as a high-water mark covering every message sent so far (system prompt and context files included). `effective_context_tokens()` returns that anchor plus an estimate of only the messages appended since, so the heuristic's error applies to the recent delta rather than the whole history. `needs_compaction`, the status-bar percentage and the manual `/compress` gate all read it. The anchor is dropped on compaction (message indices shift) and `/clear`, and a zero usage report is ignored so providers that don't report usage fall back to the running estimate. New fields are serde(default) for backward-compatible session loading. - fix(session): weight CJK/wide chars in tokenizer-free estimate_tokens The `estimate_tokens` heuristic used `bytes / 4`. That works for Latin text (~1 byte/char, ~4 chars/token) but is fragile for CJK: it only lands in a sane range because a CJK codepoint is 3 UTF-8 bytes, giving ~0.75 tokens/char, the low end of the real range. The obvious "fix" of swapping `len()` for `chars().count()` is a trap: it drops to ~0.25 tokens/char and underestimates CJK by ~3x. Classify each char as wide (CJK ideographs, kana, hangul, fullwidth forms) or narrow instead. Wide chars are weighted ~0.9 token each, slightly conservative, since underestimating context delays compaction, which is worse than overestimating, and narrow chars keep the /4 rule. Pure-ASCII input yields the exact same number as before.
