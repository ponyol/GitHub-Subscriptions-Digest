The update addresses critical data integrity issues, notably fixing `file_already_mined` to prevent duplicate data generation and unbounded storage growth by correctly identifying already-mined files. It also resolves a `KeyError` when opening existing collections due to a missing `_type` field in ChromaDB configurations. Key improvements to entity detection include a new lexicon for atomic multi-word product names and a COCA content-word filter to reduce false positives. --- Обновление устраняет критические проблемы целостности данных, в частности, исправлена функция `file_already_mined`, что предотвращает генерацию дублирующихся данных и неограниченный рост хранилища за счет корректного определения уже проанализированных файлов. Также устранена ошибка `KeyError` при открытии существующих коллекций, вызванная отсутствием поля `_type` в конфигурациях ChromaDB. Ключевые улучшения в обнаружении сущностей включают новый лексикон для атомарного распознавания многословных названий продуктов и фильтр COCA для отсеивания общеупотребительных слов, снижающий количество ложных срабатываний.

Each group carries its own stored source_mtime and normalize_version. `file_already_mined` previously used `collection.get(where={"source_file": X}, limit=1)` in the `extract_mode is None` branch and only checked the single returned row's metadata. ChromaDB's `get(..., limit=1)` has no ordering guarantee across multiple matching rows, so the returned row was effectively arbitrary. When ChromaDB happened to return a stale group (older mining pass with a different stored mtime), the function returned False, the additive miner concluded the file had changed, and wrote yet another duplicate group of drawers for a file that had not actually changed since the last successful mine. Steady-state failure: for any source_file that has ever been edited (so that the palace contains groups with different stored mtimes), each re-mine has a probability of spuriously concluding "file changed" and writing another duplicate group. Each spurious group compounds the problem because its stored mtime can also trigger the next spurious re-mine. Storage grows without bound; search results, hallway counts, and entity-frequency stats become inflated proportionally. The fix mirrors the paginated-iteration pattern already used in the `extract_mode is not None` branch — iterate every drawer for the source_file in 1000-row pages, short-circuit on the first matching group. A correct group is one that passes the existing checks: normalize_version not stale; if check_mtime, stored source_mtime within 0.001 seconds of the current file mtime. The two branches (extract_mode is None vs set) collapse into one loop that skips the extract_mode check when no extract_mode was specified. Trade-off: average-case cost rises from O(1) limit=1 query to O(N/1000) paginated scan. For typical sources (1-3 groups) the cost is unchanged because the loop short-circuits on the first matching group within the first page. For pathological sources with thousands of groups, the cost is O(number-of-pages-until-match) — still bounded, no longer flaky.
