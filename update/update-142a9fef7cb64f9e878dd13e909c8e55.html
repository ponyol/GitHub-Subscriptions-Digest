- feat: add Exa AI-powered search provider (#24) Adds a new web provider backed by the Exa search API. Until now, neither builtin nor crawl4ai supported `WebProvider.search()` — both raised NotImplementedError, leaving `hyperresearch research` unable to find sources without the user piping URLs in by hand. ExaProvider fills that gap with neural-ranked search and contents returned in a single request. - src/hyperresearch/web/exa_provider.py: ExaProvider class - src/hyperresearch/web/base.py: register "exa" in get_provider() - pyproject.toml: optional dependency `[exa]` -> exa-py>=2.0.0 - tests/test_web/test_exa_provider.py: 12 unit tests with mocked SDK Co-authored-by: Teo <teo@exa.ai> - v0.8.6: run-to-run safety — sync collision fix (#25), archive-run, vault-tag (#28) * fix(sync): drop frontmatterless scratch files; detect id collisions (#25) compute_sync_plan was scanning every .md under research/ and deriving the id from the file stem when frontmatter was absent. Agent scratch files (interim-report-<locus>.md body files, evidence-digest.md, nested run-dir scratch) collided on id with the canonical notes created from them, and the UPSERT race smashed the canonical row's `path` field. Co-Authored-By: Claude Opus 4.7 (1M context) <noreply@anthropic.com> * feat(archive-run): preserve prior-run artifacts before next /hyperresearch A second /hyperresearch invocation in the same vault used to silently overwrite scaffold.md, prompt-decomposition.json, loci.json, comparisons.md, all 4 critic-findings JSONs, patch-log.json, polish-log.json, readability-{recommendations,decisions}.json, corpus-critic-gaps.json, and the entire research/temp/ scratch tree. Only the final report and canonical query file are namespaced by vault_tag and survive across runs; everything else gets clobbered, so the prior run's audit trail and the orchestrator's working scratch are lost. The new `hyperresearch archive-run` command moves the whole set into research/runs/archive-<prev-tag>-<UTC-timestamp>/ before the next run starts. Previous vault_tag is inferred from the most recent research/query-*.md (falling back to a scaffold.md regex, then to a timestamp-only dir name). research/temp/ is recreated empty so the next run can write into it without an extra mkdir. No-ops cheaply on a fresh vault. Wired into the entry skill bootstrap as step 0.5 (runs after auto-init, before the canonical-query write). Limitation: protects sequential runs only. Two /hyperresearch invocations that overlap in time still race on the new files they both write — a real fix for that requires moving all per-run artifacts under research/runs/<vault_tag>/, which touches ~50 skill / agent / lint files. Co-Authored-By: Claude Opus 4.7 (1M context) <noreply@anthropic.com> * feat(vault-tag): collision-safe vault_tag via random 6-hex suffix Before this commit, the entry skill's bootstrap step 2 had the LLM generate a short topical slug (e.g. `efield-dft-sac`) and used it verbatim as the vault_tag. That slug is the keying material for `research/query-<tag>.md` and `research/notes/final_report_<tag>.md`, so two scenarios silently destroyed prior work: 1. User re-runs the same query → identical slug → second run overwrites the prior final report. 2. Two different queries slug-collide on shared lexical material → same outcome. `hyperresearch vault-tag <slug>` appends a random 6-hex-char suffix (16M-name space) and verifies the result is unique against every `research/query-*.md` and `research/notes/final_report_*.md` already in the live vault. Retries on collision (astronomically unlikely but bulletproof). Output: `{"vault_tag": "efield-dft-sac-a3f9b7", ...}`. Bootstrap step 2 in the entry skill now instructs the orchestrator to slug as before, then pipe through `hyperresearch vault-tag <slug> --json` to mint the final disambiguated tag. Legacy without-suffix tags from older vaults can't collide with the new format by construction (different shape).
