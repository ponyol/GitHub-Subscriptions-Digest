- fix: interrupts: replay legacy GSI allocations on restore This is a follow-up from PR #5952, where we replayed MSI-X GSI allocations on snapshot restore, to ensure all of the handed out GSIs are valid at restore time. As part of that PR, we changed the `IdAllocator` struct to use a bitmap, backed by the `BitVec` struct from `bitvec` crate. `bitvec`'s implementation of serde deserialization doesn't handle malformed input gracefully, panicking instead of returning an error. Under normal conditions, where a well-formed snapshot is provided, such panics would never occur, but we would like to avoid a panic even under such conditions. To do this, we mirror the changes in #5952, creating a new `IdAllocator` on restore for the legacy GSIs, and replay allocations. This prevents us ever serializing bitvec and encountering this condition, with the added benefit of standardising behaviour across both GSI allocators. Signed-off-by: James Curtis <jxcurtis@amazon.co.uk> - fix: validate PCI MSI-X interrupts on snapshot restore Previously, malformed snapshots could contain MSI-X GSI values that were never handed out by the restored `gsi_msi_allocator`, or could assign the same GSI to multiple vectors/devices. The state of the allocator was only verified when `MsixVectorGroup::drop` called `IdAllocator::free_id` To fix this, replay allocations on snapshot restore. That way, any issues with the snapshot state will cause an error at restore time, rather than allowing the VM to execute with potentially 'bad' interrupts. The ResourceAllocator now does not serialize the gsi_msi_allocator, instead creating a new one on restore. ResourceAllocatorState has now been introduced as a result, containing all of the ResourceAllocator fields except the gsi_msi_allocator. Signed-off-by: James Curtis <jxcurtis@amazon.co.uk> - resources: vendor IdAllocator from vm-allocator For snapshotting purposes, we require the ability to allocate arbitrary IDs, which he upstream crate does not currently allow for. The internals of the IdAllocator are re-implemented to use a bitmap to track currently allocated IDs. This is acceptable for our purposes, as the maximum number of ID is bounded to 4096, so the bitmap can be at most 512B. This implementation is likely unsuitable for upstreaming, since the upstream version of IdAllocator can allocate up to u32::MAX, so for now we will keep it downstream.
