Суммаризация (на русском)

Этот выпуск содержит значительные улучшения для языка Mojo, фреймворка MAX и ядер. Стандартная библиотека Mojo широко переходит на более безопасные типы `Pointer` и вводит `where`-выражения с пользовательскими сообщениями об ошибках, а также улучшенную арифметику литералов. Для MAX обновления включают существенные улучшения XGrammar для обработки EOS-токенов, структурированного вывода (особенно для Gemma 4) и исправления производительности/стабильности для KV-кэша, поддерживаемые новым коннектором на Rust. Оптимизации на уровне ядер добавляют нативную поддержку FP8 для SM100, повышения производительности для AMD и новые операции редукции.

MODULAR_ORIG_COMMIT_REV_ID: 1eb63241104fe95c357749989c55a3e0603e5ad9 - [mojo-lang] Support custom messages on `where` clauses Adds an optional failure message to Mojo `where` clauses, written `where (condition, "message")`. When the constraint fails, the message is surfaced in the compiler diagnostic. Supported everywhere `where` clauses are allowed: trailing function, struct, and `comptime` alias constraints, and struct conditional-conformance clauses (`struct S(Trait where (cond, "msg"))`). ```mojo def foo[sc: Int]() where (sc > 1, "scaling factor must be greater than 1"): ... ``` Calling `foo[0]()` now reports: ```text note: constraint declared here evaluated to False, expected '(sc > Int(1))': scaling factor must be greater than 1 ``` ### Design notes - The parentheses make the message unambiguous against the conformance-list entry separator — the message is simply the second element of a two-element tuple expression, so no lookahead is needed. - String-literal messages only for now. `where` clauses are handled by the parser, which has no interpreter, so a non-literal message (e.g. `"got " + String(N)`) can't be evaluated at that phase and is a targeted error. The parenthesized syntax leaves non-literal support as a backward-compatible extension. - Messages surface for body constraints (the violated / "needs evidence" notes) and for conditional-conformance failures (the "does not conform to trait" notes). Conformance messages are evaluated under the caller's assumptions — a conformance the caller proved via its own `where` clause is not reported — and are carried down to auto-propagated ancestor traits. Full design writeup is the "Failure messages" section of `oss/modular/mojo/proposals/where_clauses.md` (this re-adds the message field that was removed on 2025-10-01). ### Testing New lit tests under `KGEN/test/mojo-parser/decls/where_message*.mojo` (parse, diagnostics, negative parse, conditional conformance), an attribute round-trip in `kgen-attrs.mlir` covering the `#kgen.constraint` message field (textual and bytecode), and `mblack` formatter tests. Conversely a successfully-imported module would occupy the same spot in that cache. This conceptual model has a few issues. For starters, we want to prevent module self-imports in future work. But the module being compiled is (obviously) cached, so we are unable to report an erroneous import using this cache. Secondly, by caching erroneous modules we were preventing retries and under-reporting errors. This has an effect in things like the REPL, LSP, etc., where one unsuccessful import would prevent the user from fixing the issue and retrying. This this commit, failed imports no longer masquerade as modules. Erroneous states are split from the per-scope module cache into their own map. This has a couple of user-visible consequences: 1. In an interactive environment (e.g., the RPEL) this means a user can fail to import a module then fix the issue (`%cd` into the right directory or fix the problem) and retry the import. 2. Every import site reports errors, so that on a retry if the issue still persists the error will be reported anew. This should also hopefully improve diagnostic quality in compilation, for example, where a bad import will now be emitted closer to the file the user cares about and not only on its first use (which may be in another package). Note now that lookup invisibility now applies to any name whose decls are all disabled. Today this only applies to imports as they act as tombstones, but in theory applies to any name with disabled decls such as trait methods. This lookup is only performed on names with disabled decls and is marked "unlikely" to keep the action fast. This could also have a marginal effect on the compilation times of erroneous modules as we'll have to go back to the filesystem, etc., but since we're already erroring it's not the fast path and does enable some legitimate behaviours detailed above.
