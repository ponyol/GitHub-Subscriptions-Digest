- CI: fail the notebook-tests job when a changed notebook fails to execute (#772) The maintainer-gated execution step in notebook-tests.yml runs each CHANGED notebook against the live API and counts failures, but nothing ever read that count: the step never exits non-zero (each per-notebook failure is absorbed by its if/else), it carries continue-on-error, and the "Final status check" that actually fails the job only looked at the structure-test result. So a notebook that 400s at runtime went green. That is exactly how #375 shipped a metaprompt notebook that fails on its first API call for every user. This wires the execution result into the gate: - The execution step always writes its exec_failures count as a step output (previously it only wrote it when non-zero, so "0 failures" and "did not run" were indistinguishable downstream). - The Final status check fails the job when exec_failures is greater than zero. - The Final status check also fails the job when the execution step's own outcome is 'failure', meaning its SCRIPT errored under continue-on-error. Without this, a script error leaves exec_failures unwritten and reads exactly like a clean skip, so a broken execution harness would look identical to a passing one. External contributors are unaffected: for a fork PR the execution step is skipped by its `if:`, and when the API key is absent it early-exits before writing any output. In both cases the step's outcome is not 'failure' and exec_failures is empty, so neither new gate fires. This was verified by running the Final status check script under bash with all six input combinations the workflow can produce; the three skip/clean cases pass and the three failure cases each exit 1 with the right message. continue-on-error stays on the execution step so the artifact-upload step still runs; the gate now lives where this workflow already puts it, in the Final status check. Deliberately NOT changed here: the separate all-notebooks execution step in notebook-quality.yml. It has never authenticated (its API key env var is miscased) and it swallows every failure, but fixing only the casing would start executing all 89 notebooks against the real API on every member PR and push to main while still producing no CI signal, and its static-secret auth is on a deprecation path in favor of Workload Identity Federation regardless.
