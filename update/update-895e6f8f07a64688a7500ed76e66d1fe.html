Это обновление для `vulpea` повышает надежность базы данных за счет нормализации путей к файлам macOS и обеспечения корректной загрузки в рабочих процессах, а также улучшает мониторинг внешних файлов. - docs(plugin-guide): clarify that custom note-data keys are transient The guide said extractors can add custom keys to note-data for other extractors to use, which reads as if those keys get persisted. They do not: only fields in vulpea-db--note-field-columns are written back, unknown keys are silently ignored (#382). State the transience explicitly, and add a Storing Per-Note Data section with the recipes for data that should survive: a 1:1 side table keyed by note-id, a generic (note-id, axis, value) table for multiple axes, or a property/meta entry in the file itself. - fix(db): normalize file paths to NFC on macOS (#383) Paths from fd/find/fswatch subprocesses arrive as raw NFD bytes while filename syscalls decode to NFC via utf-8-hfs, so the database kept two independently-updated rows per non-ASCII file name. Since note inserts are OR IGNORE, the fresh row never replaced the legacy one, and consumers reading through the stale row saw old hashes and metadata (publicatorg missed edits to such notes entirely). New vulpea-db-path-normalization (default nfc on darwin) canonicalizes paths at every entry point, and cleanup purges legacy rows keyed by non-canonical paths, forcing a re-index of affected files. - fix(db-worker): force load-prefer-newer in the worker process (#381) The worker spawns with -Q, so a stale .elc next to a newer .el loaded in the worker while the main process ran the source, and the two processes silently executed different versions of vulpea. Set load-prefer-newer before the worker loads anything. - fix(db-sync): do not resurrect fswatch after external monitoring stops The fswatch sentinel auto-restarts a died process via a 2-second timer. Stopping external monitoring killed the process without detaching that sentinel, so the watcher respawned after the stop, using whatever vulpea-db-sync-directories was current at that moment (the org-directory default in the test suite, which leaked a watcher on ~/org for the rest of the run). Detach the sentinel before killing and cancel an already-scheduled respawn. - docs(mentions): polish ignore-property wording, add CHANGELOG entry - feat(mentions): ignore mentions for notes with the ignore property (#378) A note with the MENTIONS property set to ignore (both customizable via vulpea-mentions-ignore-property-key/-value) opts out of mentions: its own incoming scan short-circuits, and it is dropped from the outgoing candidate dictionary, so its title is never searched for. Closes #369 (idea 1). - fix: signal user-error when vulpea-create title is not a string (#380) Passing a nil (or otherwise non-string) title to vulpea-create used to fail deep inside content formatting with a cryptic wrong-type-argument, which reads as a silent rejection in wrapped flows. Fail loudly and early instead: titles are a structural invariant (derived from the org source on every sync), so a nil title can never work. Refs #379 - feat(db-sync): add vulpea-db-sync-tracked-file-p, resolve symlinks (#377) Add a public predicate answering whether a path lives under one of vulpea-db-sync-directories. It resolves both the path and the directories with file-truename before comparing, so a vault reached through a symlink (a Termux storage link, an iCloud or Dropbox path) matches whichever side carries the link. Route the two internal callers through it: the untracked-file cleanup (previously file-in-directory-p) and the fswatch path filter (previously a string-prefix-p over expand-file-name, which did not resolve symlinks). The fswatch one carried a latent bug on macOS, where fswatch reports the resolved path that a symlinked directory entry would not match, so external changes under such a vault were dropped. - Update README with additional vulpea links - docs(mentions): polish wording around linked-note exclusion Rewrite the defcustom and helper docstrings (one sentence went stale when the exclude-linked check moved to the call site), explain why only bracket id: links form the exclusion set, and move the CHANGELOG entry from the already-released v2.6.0 section to Unreleased. - feat(mentions): exclude mentions to/from explicitly linked notes (#374) Once a note links to another, later plain-text occurrences are not a missing connection, so they no longer show up as unlinked mentions. Incoming mentions drop hits from files the DB already knows link to the note; outgoing mentions drop candidates whose id: link is already present in the live buffer content. Set vulpea-mentions-exclude-linked to nil to restore the old behavior. Closes #369 (idea 3).
