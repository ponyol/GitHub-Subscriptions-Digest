Two consequences of the conflation: * Reads that emit usage metrics (e.g. `databases.operations.reads` from `Documents/{XList,Get}`) can't tag correctly without accidentally enabling audit logging on every list/get. The shutdown fallback then tags those reads with `resource='project'`, `resourceId=<projectId>` — wrong for a database-scoped metric. * The two labels can legitimately want different shapes — an audit row may want the full hierarchical path down to a document id; usage tagging only consumes the first two slash-segments. Sharing one label couples the consumers together. Introduce a dedicated `usage.resource` label with the same shape as `audits.resource` (`<resource>/<idTemplate>[/<deeper>...]`). The first two segments drive the usage Context's `resource` and `resourceId`. Applied to: * Every route that already carries `audits.resource` — verbatim mirror of the value.
