Это обновление значительно повышает производительность и стабильность Firecracker, в частности, за счет исправления ошибки VSOCK, вызывавшей активное ожидание при нехватке RX-буфера гостевой ОС, и устранения паники при восстановлении ACPI-устройства. Signed-off-by: Riccardo Mancini <mancio@amazon.com> - fix(vsock): stop busy-spinning the event thread on guest RX starvation An Established vsock connection kept advertising level-triggered EPOLLIN in get_polled_evset() even when it already had an undeliverable PendingRx::Rw queued. Once a host-side application wrote data (or closed its end) and the guest stopped posting virtio RX buffers, the muxer's nested epoll fd stayed readable, so the single-threaded event manager woke up on every epoll_wait, made no progress, and busy-spun the event thread until the guest posted buffers. Being single-threaded, this also delayed servicing of the API socket, metrics, and all other device backends. Stop re-arming EPOLLIN while an undeliverable Rw indication is pending. This drops the connection fd's IN interest in the muxer's nested epoll so the fd goes quiet and the outer event loop sleeps. The pending RX is still tracked in the muxer rxq, so when the guest refills the RX queue, process_rx() drains the packet, recv_pkt() clears the Rw indication, and apply_conn_mutation() re-arms IN. Both the data-available and host-EOF variants are covered. This resolves the queue-deadlock scenario previously flagged by a TODO in device.rs, which is removed. Signed-off-by: Riccardo Mancini <mancio@amazon.com> - vmm: fix panic on ACPI device restore when EventFd creation fails ACPIDeviceManager::restore() called .unwrap() on VmGenId::restore() and VmClock::restore(), both annotated with a comment claiming they can never fail. This is incorrect: both call EventFd::new(), which can fail (e.g. EMFILE) when the process is near its file descriptor limit, a realistic condition during snapshot-restore when many devices are being reconstructed. A failure here would panic and crash Firecracker instead of returning a graceful error. ACPIDeviceError already has #[from] conversions for VmGenIdError and VmClockError, so this replaces the two unwrap() calls with ? and removes the incorrect comments. Signed-off-by: James Curtis <jxcurtis@amazon.co.uk> - device_manager: introduce VirtioDevices enum Centralise virtio devices into a VirtioDevices enum, since the MMIO and PCI transports for virtio devices are mutually exclusive. The enum owns the transport-agnostic operations (get_device, for_each_device, kick, mark_dirty) and dispatches to the concrete MMIO/PCI managers, which are now held behind the enum rather than as separate DeviceManager fields. Boot-time attach and runtime hotplug match on the active transport at their DeviceManager call sites rather than through methods on the enum: each has a single caller, and hotplug/hot-unplug are only supported over PCI, so a method on the enum would only pair one real arm with reject arms. The ACPI builder emits virtio DSDT data through the enum's append_aml_bytes dispatch. For PCI VMs this moves the PCI segment AML ahead of the GED/VMGenID blocks in the DSDT; the reorder is benign since DSDT blocks are order-independent namespace declarations. Callers that need transport-specific state (the FDT builder's MMIO device info and PCI segment) go through the transport accessors (as_mmio, as_pci), since such callers are already implicitly transport-specific. The snapshot wire format is unchanged: save() fills both transport slots (the inactive one with its empty default) and restore() picks the transport from the pci_enabled flag. The next commit changes the format to hold only the active transport. Signed-off-by: Marco Marangoni <mamarang@amazon.com> - feat: align guest memory to 2MiB This commit align guest memory to 2MiB. The main benefit is to enable further opportunities to use THP at the head and tail of guest memory. Alignment is enabled unconditionally (rather than only with THP) for a few reasons: reduce modalities, performance benefit when THP is enforced by the system rather than Firecracker (e.g. `/sys/kernel/mm/transparent_hugepage/enabled` = `always`), and because there's no downside of doing so. This implementation doesn't make assumptions on the guest memory size, so extra considerations had to be taken when it is not a multiple of page-size. This is required since several tests currently rely on guests of specific sizes.
