Суммаризация (на русском)

Это обновление устраняет несколько критических проблем в редакторе Lem, в основном связанные с зависаниями и сбоями nREPL-соединения в `clojure-mode`, а также взаимодействием `lsp-mode` с буферами без языковых спецификаций. Для `clojure-mode` исправления включают предотвращение взаимоблокировок при синхронных nREPL-запросах, обеспечение надежного запуска сессии и корректное соблюдение таймаутов для поддержания отзывчивости редактора. Кроме того, `lsp-mode` теперь корректно обрабатывает буферы без языковой спецификации, предотвращая сбои и запуск ненужных LSP-процессов в таких контекстах, как REPL-буферы. Улучшения стабильности также исправляют зависания и сбои в команде `describe-bindings`.

- fix(clojure-mode): deadlock in nrepl-send-sync hangs clojure-connect (#2191) * fix(clojure-mode): deadlock in nrepl-send-sync hangs clojure-connect clojure-connect and clojure-connect-to-localhost would hang the editor forever even when the nREPL server was listening and replying. Root cause: nrepl-send-sync runs on the main thread inside nrepl-connect and blocks in (loop :until done (bt:condition-wait cv lock :timeout T)). The reader thread routed the response handler through send-event, which queues it onto the main thread's event loop -- but the main thread is blocked in condition-wait and cannot pump that queue. The handler that sets done=t and notifies the cv therefore never runs. The :timeout on condition-wait does not help: the outer loop just re-enters. Fix: split response handlers into sync and async tables. Sync handlers (registered by nrepl-send-sync) are invoked directly on the reader thread so synchronous callers can be notified without depending on the main thread's event loop. Async handlers (the existing nrepl-send callback path, e.g. repl-handle-response) still go through send-event, because they touch buffers and must run on the main thread. Follow-up improvement: a cleaner long-term design is to give sync messages a dedicated reply channel that bypasses the shared response-handlers dispatch entirely (rather than maintaining two parallel tables on the connection). Left for a separate change. * fix(clojure-mode): start reader thread before first sync request The reader thread was spawned *after* nrepl-clone-session-sync ran, so the very first synchronous request inside nrepl-connect had no one draining the socket: the server's reply sat in the kernel receive buffer and the main thread blocked on condition-wait forever. Start the reader thread immediately after the socket is open and before any nrepl-send-sync call. Combined with the previous commit (which routes sync handlers off the main thread), the synchronous session clone in nrepl-connect now completes instead of hanging. * fix(clojure-mode): honor timeout in nrepl-send-sync The :timeout argument on bt:condition-wait fires correctly, but the outer (loop :until done ...) simply re-entered condition-wait every iteration, so the timeout was effectively useless: a server that accepted the connection but never replied (wrong port, non-nREPL listener, hung process) hung the editor's main thread indefinitely. Track a real deadline at entry and compute the remaining time each iteration. When it reaches zero, signal an editor-error explaining that the request timed out. Also drop the registered sync-response handler in an unwind-protect, so a late reply after timeout does not push onto a stale closure and the table does not grow over time. With this change, a misconfigured port now surfaces a clean "nREPL request clone timed out after 30 seconds" error and the editor remains responsive, instead of freezing. * fix(clojure-mode): bootstrap nREPL session synchronously on main thread nrepl-connect used to start the reader thread first and then call nrepl-clone-session-sync, which depended on the reader thread to deliver the clone response via a condition variable. Under Lem's event loop that cross-thread handoff stalls -- the reader thread observes only the first byte of bb's reply and the next read-byte never returns, even though the same code outside Lem reads the full ~100-byte response in milliseconds (verified standalone). Do the connect handshake inline on the calling thread instead: write the clone op, then read-bencode-message in a loop on the same thread until the response with status \"done\" arrives. Start the reader thread only after the session is established, when it only needs to service asynchronous response delivery. This matches what other nREPL clients do during bootstrap and is the exact pattern that succeeds in the standalone usocket reproducer. nrepl-send-sync (used by nrepl-eval-sync etc.) keeps its existing reader-thread + cv design; if the same stall affects those calls, it will be addressed separately. * fix(clojure-mode): treat truncated bencode as incomplete, not fatal read-bencode-message reads one byte at a time and re-decodes the accumulated buffer after each byte, expecting bencode-error while the message is incomplete and a successful decode when the byte count is sufficient. The actual bencode decoder, however, signals end-of-file (raised by peek-char on the exhausted string-input-stream backing decode), not bencode-error, when its input is truncated mid-value -- e.g. after the leading "d" of a dictionary. Our handler-case only caught bencode-error, so the very first byte of every server reply caused end-of-file to escape: - In the reader-thread design this hit the outer (end-of-file ...) handler of nrepl-reader-loop and silently killed the reader after one byte, which is why bb's full clone-session response never reached the waiting main thread. - In the synchronous bootstrap path added in the previous commit it surfaced as an unhandled end-of-file backtrace at the user. Catch end-of-file alongside bencode-error in the byte-at-a-time loop and continue reading. Both conditions mean "buffer not yet a complete bencode value." * fix(clojure-mode): suppress lsp-mode on the REPL buffer clojure-repl-mode inherits from clojure-mode, so Lem's major-mode activation invokes the parent mode as part of the child's setup (mode.lisp around line 157). That parent step fires *clojure-mode-hook*, which contains enable-lsp-mode (added by define-language-spec in lsp-config.lisp), so lsp-mode is turned on briefly while the buffer is under clojure-mode -- which kicks off an async workspace connect for clojure-lsp. The lsp-mode hardening in the previous commit prevents that workspace from crashing the editor when the REPL buffer no longer has a language spec, but it still leaves an unnecessary clojure-lsp process attached to a buffer where LSP cannot do anything useful. Disable lsp-mode in the clojure-repl-mode body so the REPL transcript does not even attempt LSP attachment. The call goes through find-package + uiop:symbol-call so clojure-mode does not hard-depend on lem-lsp-mode being loaded. * style(clojure-mode): use :do keyword in bare loops Address code-contractor loop_keywords_rule on PR #2191. The assertion crashed the editor command loop whenever a buffer's major mode lacked a registered spec. This is reachable in normal use. clojure-repl-mode (and similar listener-style modes) inherits from clojure-mode, which registers a spec.
